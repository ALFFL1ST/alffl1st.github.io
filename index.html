自编译老内核kernelsu经验总结

发表于 2026-07-29

Xperia XZ1 (poplar) LineageOS 18.1 / KernelSU-Next 构建与排障记录

1. 目标

在 Sony Xperia XZ1 poplar（G8341/SOV36）上完成以下工作：

  1. 构建可启动的 Linux 4.4.302 基线内核。
  2. 使用当前 PixelExperience Android 11 的 ramdisk 验证自编译内核。
  3. 集成适用于 Linux 4.4 的 KernelSU-Next。
  4. 最终让 KernelSU Manager 能识别内核并实际授予 root 权限。

目前已经完成内核基线验证、KernelSU-Next 编译和临时启动验证。KernelSU 功能层面的 root 授权仍待最终验证。

2. 环境信息

2.1 构建主机

  • 系统：Ubuntu 24.04.4 LTS
  • 内核：Linux 6.8.0-136-generic x86_64
  • 内存：15.6 GB RAM
  • Swap：2 GB
  • Android 源码：~/android/lineage-18.1
  • 构建目标：lineage_poplar-userdebug
  • Android 平台：Android 11 / LineageOS 18.1
  • 构建并发：-j2

构建系统会提示内存低于建议的 16 GB。当前使用 -j2 可以降低 Soong、Ninja 和内核并行编译造成的内存压力。

2.2 设备

  • 设备：Sony Xperia XZ1
  • 设备代号：poplar
  • 型号属性：G8341 / SOV36
  • bootloader：已解锁
  • 当前 ROM：PixelExperience Plus Android 11
  • Android SDK：30
  • fastboot 序列号：QV702UFT11
  • fastboot 支持临时启动：fastboot boot

当前正常启动的是原 PixelExperience boot，Magisk root 可用：

uid=0(root) gid=0(root) groups=0(root) context=u:r:magisk:s0

3. 源码准备

3.1 Android 源码

LineageOS 18.1 主源码已经同步完成，设备相关目录包括：

device/sony/poplar
device/sony/yoshino-common
kernel/sony/msm8998
vendor/sony/poplar

设备树采用 whatawurst 的 LineageOS 18.1 实现。

3.2 内核源码

内核源码目录：

~/android/lineage-18.1/kernel/sony/msm8998

内核来源 commit：

85139e3d7b8dce1fd285c68f09469cc3e9af3902

版本：

Linux 4.4.302

使用的 defconfig：

arch/arm64/configs/lineage-msm8998-yoshino-poplar_defconfig

由于 Git pack 下载经常发生网络中断，内核最终通过指定 commit 的源码压缩包获取，然后在本地初始化 Git 仓库。

3.3 Proprietary vendor

TheMuppets 对应分支中没有可直接使用的 poplar vendor，因此使用 root ADB 从当前 PixelExperience 系统提取 proprietary 文件，并生成：

vendor/sony/poplar/poplar-vendor.mk

4. CTS 稀疏检出问题

4.1 问题

为了减少下载量，CTS 使用了 partial clone 和 sparse checkout。构建过程中出现多个缺失模块，之后又在 Kati 阶段失败：

test/vts/tools/build/tasks/framework/vtf_package.mk:83:
error: FindEmulator: cd: cts/apps/CameraITS: No such file or directory

ALLOW_MISSING_DEPENDENCIES=true 只能跳过缺失的构建依赖，不能解决 Makefile 中直接执行 cd 访问不存在目录的问题。

4.2 解决方法

使用非 cone sparse checkout 精确补齐目录：

git -C cts sparse-checkout add '/apps/CameraITS/'

验证：

test -d cts/apps/CameraITS && echo camera-its-ok

4.3 知识点

  • ALLOW_MISSING_DEPENDENCIES 只影响构建图中的模块依赖检查。
  • Makefile 内部的 shell 命令仍要求实际路径存在。
  • 对大型 Android 仓库，partial clone 可以减少 Git object 下载量，sparse checkout 可以减少工作树占用。
  • 当错误形式为 module not found 时，可以考虑依赖绕过；当错误形式为 cd: path: No such file or directory 时，必须补齐真实路径。

5. 基线 boot 构建

构建命令：

source build/envsetup.sh
lunch lineage_poplar-userdebug
export ALLOW_MISSING_DEPENDENCIES=true
mka bootimage -j2 2>&1 | tee build-boot.log

构建成功：

[100%] Target boot image: out/target/product/poplar/boot.img
build completed successfully

生成文件：

out/target/product/poplar/boot.img
out/target/product/poplar/obj/KERNEL_OBJ/arch/arm64/boot/Image.gz-dtb

5.1 非致命警告

构建期间出现以下警告，但未阻止镜像生成：

  1. Clang 提示 -fuse-ld=lld 在部分 host 编译中未使用。
  2. Ubuntu 24.04 的 OpenSSL 3.0 将部分 ENGINE API 标记为 deprecated。
  3. scripts/gcc-version.sh 无法执行部分 GCC 4.9 预编译工具。
  4. nsjail 不可用，构建 sandbox 被禁用。

这些信息不能单独视为构建失败。判断结果应以 Ninja/Make 最终退出状态以及目标产物是否生成作为依据。

6. 为什么 LineageOS boot 无法直接启动当前 PE

首次通过以下命令临时启动 LineageOS 生成的完整 boot：

fastboot boot ~/android/artifacts/poplar/boot-lineage18.1-baseline.img

设备卡在 Sony 第一屏。强制重启后重新进入原 PixelExperience。

6.1 根因

Android boot image 不只有内核，还包含 ramdisk。LineageOS boot 中包含 LineageOS ramdisk，而设备 system 分区仍然是 PixelExperience。

以下组件可能不匹配：

  • init 配置
  • fstab
  • SELinux policy 装载流程
  • vendor service 启动规则
  • system/vendor/ramdisk 之间的接口

所以“LineageOS boot 无法启动 PE system”不能证明新内核有问题。

6.2 恢复方法

fastboot boot 是临时加载，不会覆盖 boot 分区。设备可通过以下方式恢复：

长按 电源键 + 音量上键，直到连续震动三次

重新正常开机后仍会使用原 boot 分区。

6.3 知识点

  • fastboot boot image.img：临时启动，通常不写分区，适合测试。
  • fastboot flash boot image.img：永久写入 boot 分区，测试阶段不应优先使用。
  • 单独替换 boot 并不等于安装完整 ROM。
  • 验证“内核是否可启动”时，应尽量保持 ramdisk 和 system 不变，只替换 kernel。

8. KernelSU-Next 集成

8.1 Git 基线

内核来自 tarball，因此先初始化本地 Git：

git -C kernel/sony/msm8998 init
git -C kernel/sony/msm8998 add -A
git -C kernel/sony/msm8998 commit -m "Baseline whatawurst kernel 4.4.302"

这样可以在 KernelSU 修改失败时准确查看差异或回退。

8.2 v3.3.0 失败

KernelSU-Next setup 脚本默认检出最新 tag，当时为 v3.3.0。

编译错误：

unknown type name 'syscall_fn_t'
fatal error: 'linux/compiler_types.h' file not found

根因

v3.3.0 的 arm64 syscall hook 依赖较新的 syscall wrapper ABI，包括：

  • syscall_fn_t
  • __arm64_sys_* 风格 syscall
  • 新版 syscall table 调用约定
  • 新内核头文件 linux/compiler_types.h

Linux 4.4 的 arm64 syscall table 和函数签名与新内核不同。该问题不是补一个 typedef 就能安全解决，因为实际调用 ABI 也不一致。

解决方法

放弃 v3.3.0，改用带 legacy 后缀的旧内核兼容 tag。

8.3 v3.2.0-legacy

选用：

v3.2.0-legacy

启用配置：

CONFIG_KPROBES=y
CONFIG_KSU=y

同时已有：

CONFIG_EXT4_FS=y
CONFIG_OVERLAY_FS=y
CONFIG_KALLSYMS=y

8.4 Linux 4.4 兼容补丁

问题一：ERR_PTR 隐式声明

错误：

include/linux/bpf.h: implicit declaration of function 'ERR_PTR'
static declaration of 'ERR_PTR' follows non-static declaration

根因：KernelSU 的 setuid_hook.c 在包含 linux/err.h 前包含了 linux/bpf.h。该 4.4 内核的 bpf.h 假设 ERR_PTR 已经声明。

解决：在 linux/bpf.h 前加入：

#include <linux/err.h>

文件：

KernelSU-Next/kernel/hook/setuid_hook.c

问题二：不存在的 sched UAPI 头文件

错误：

fatal error: 'uapi/linux/sched/types.h' file not found

根因：uapi/linux/sched/types.h 不存在于当前 Linux 4.4 树。

解决：删除该 include：

#include <uapi/linux/sched/types.h>

文件：

KernelSU-Next/kernel/selinux/rules.c

问题三：in_compat_syscall() 不存在

错误：

implicit declaration of function 'in_compat_syscall'

根因：该 API 来自较新内核，Linux 4.4 arm64 使用 is_compat_task() 判断当前是否为 compat 任务。

解决：

in_compat_syscall()

替换为：

is_compat_task()

文件：

KernelSU-Next/kernel/runtime/ksud_integration.c

这证明集成 KernelSU 的内核本身能够完成启动，但不等于 KernelSU 用户空间授权流程已经验证成功。

10. KernelSU Manager 问题

10.1 原 Manager 实际不是 KernelSU-Next

设备原先安装的包：

package: me.weishu.kernelsu
versionName: v3.0.0
versionCode: 32179
minSdk: 26
targetSdk: 36

该版本属于官方 KernelSU Manager，而不是 KernelSU-Next 对应发行包。

10.2 原 Manager 闪退根因

隔离 NFC 日志后捕获到：

Fatal signal 31 (SIGSYS)
code 1 (SYS_SECCOMP)
Cause: seccomp prevented call to disallowed arm64 system call 142
process: libksud.so

这说明闪退不是普通 Java 异常，而是 Manager 内置的 libksud.so 调用了 Android 11 应用 seccomp 策略不允许的 syscall 142，被内核发送 SIGSYS 强制终止。

10.3 KernelSU-Next v3.2.0 Manager 无法安装

错误：

INSTALL_FAILED_OLDER_SDK
Requires newer sdk version #31 (current version is #30)

原因：

  • KernelSU-Next v3.2.0 Manager 要求 Android 12 / SDK 31。
  • 当前 PixelExperience 是 Android 11 / SDK 30。

这属于 APK manifest 的最低 SDK 限制，与内核是否支持 KernelSU 无关。

10.4 KernelSU-Next v3.0.1 Manager

下载地址：

https://github.com/KernelSU-Next/KernelSU-Next/releases/download/v3.0.1/KernelSU_Next_v3.0.1_32967-release.apk

本地路径：

/tmp/KernelSU_Next_v3.0.1.apk

该版本可以安装在 Android 11，并且不再出现原官方 v3.0.0 Manager 的 libksud.so seccomp 闪退。

它在设备运行原 Magisk boot 时提示：

无法在内核中找到 KernelSU v2 签名

该提示目前不能视为 Manager 与 v3.2.0-legacy 内核不兼容，因为看到提示时设备已经重启回原 PE/Magisk boot。原 boot 本来就没有 KernelSU。

正确验证方式是：临时启动 boot-pe-kernelsu-legacy.img 后，再打开 KernelSU-Next v3.0.1 Manager。

11. NFC 崩溃对诊断的干扰

PE 当前还有独立 NFC 崩溃循环：

com.android.nfc
android.hardware.nfc@1.1-service
libnfc-nci.so
nfc_nci_nxp.so

NFC 服务会快速生成 tombstone，覆盖 KernelSU Manager 的崩溃记录。

为了隔离日志，执行过：

adb shell "su -c 'setprop ctl.stop vendor.nfc_hal_service'"
adb shell "su -c 'am force-stop com.android.nfc'"

验证状态：

adb shell getprop init.svc.vendor.nfc_hal_service

输出：

stopped

设备重启后 NFC HAL 通常会由 init 重新启动。

知识点

  • logcat -b crash 是环形缓冲区，频繁崩溃会覆盖旧记录。
  • 原生进程崩溃的完整信息通常位于 /data/tombstones/。
  • 排障前应先停止无关的崩溃循环，否则容易把错误归因到错误的组件。
  • 仅根据“应用闪退”现象无法判断是 Java、JNI、SELinux、seccomp 还是内核接口问题。

12. Git 提交与当前源码状态

主内核仓库已有提交：

0a1d0225 poplar: integrate KernelSU-Next
15ac5648 vendor: include KernelSU-Next sources

v3.2.0-legacy 的 Linux 4.4 兼容补丁分支：

poplar-linux-4.4-v3.2.0

补丁提交：

48876bfd compat: support Linux 4.4

为了尝试匹配 v3.0.1 Manager，嵌套 KernelSU-Next 工作树后来被切换到了：

v3.0.1-legacy
commit 1fe50d16

但该版本目前：

  • 尚未应用 Linux 4.4 兼容补丁。
  • 尚未重新编译。
  • 尚未提交进主内核仓库。
  • 因源码布局变化，主内核仓库会显示大量文件删除和新增。

在确认确实需要降级内核前，不应提交这些大范围变更。

恢复已验证 v3.2.0 源码：

git -C kernel/sony/msm8998/KernelSU-Next checkout poplar-linux-4.4-v3.2.0

13. 当前推荐验证流程

阶段一：确认 Manager

确认当前安装的是 KernelSU-Next v3.0.1，而不是原官方 v3.0.0：

adb shell dumpsys package me.weishu.kernelsu | grep -E 'versionName|versionCode|codePath'

期望 version code 接近 KernelSU-Next 发布包的 32967。

阶段二：临时启动已验证的 KSU 内核

adb reboot bootloader
fastboot devices
fastboot boot ~/android/artifacts/poplar/boot-pe-kernelsu-legacy.img

阶段三：确认内核

adb wait-for-device
adb shell uname -a

阶段四：打开 Manager

adb shell monkey -p me.weishu.kernelsu 1

检查 Manager 是否识别 KernelSU，并尝试给测试应用或 shell 授予 root。

阶段五：功能验证

验证目标不只是“应用能打开”，还应包括：

  1. Manager 能读取 KernelSU 版本。
  2. Manager 显示内核支持状态正常。
  3. 能产生超级用户授权请求。
  4. 被授权应用实际获得 UID 0。
  5. 重启和卸载模块后系统仍可恢复。

如果 v3.0.1 Manager 在 v3.2.0-legacy 内核下仍明确提示协议或签名不兼容，再考虑构建匹配的 v3.0.1-legacy 内核。

14. 安全与恢复原则

14.1 测试时只临时启动

优先使用：

fastboot boot image.img

不要在未验证前执行：

fastboot flash boot image.img

14.2 卡第一屏时恢复

长按 电源键 + 音量上键，直到连续震动三次

因为使用的是临时启动，重新开机后会回到原 PE/Magisk boot。

14.3 保留原始镜像与哈希

必须长期保留：

boot-pe-original.img
boot-pe-newkernel-baseline.img
boot-pe-kernelsu-legacy.img

每次重新打包后都应：

  1. 解包检查 header 参数。
  2. 对比打包前后的 kernel SHA-256。
  3. 检查镜像大小没有超过 boot 分区。
  4. 先临时启动，再考虑永久刷写。

15. 关键结论

  1. LineageOS boot 卡第一屏是 ramdisk/system 不匹配，不能证明内核失败。
  2. PE ramdisk + 基础 4.4.302 内核已成功启动，基础内核可用。
  3. KernelSU-Next v3.3.0 使用新版 arm64 syscall ABI，不适合该 Linux 4.4 内核。
  4. KernelSU-Next v3.2.0-legacy 经三个小型兼容补丁后成功编译。
  5. PE ramdisk + v3.2.0-legacy KSU 内核已成功启动。
  6. 原官方 KernelSU Manager v3.0.0 因 Android 11 seccomp 阻止 syscall 142 而原生崩溃。
  7. KernelSU-Next v3.2.0 Manager 要求 SDK 31，不能安装到 Android 11。
  8. KernelSU-Next v3.0.1 Manager 可安装且不再发生原 seccomp 闪退。
  9. v3.0.1 Manager 在原 Magisk boot 下找不到 KSU 是正常现象，必须在 KSU 临时 boot 下重新验证。
  10. 当前下一目标是验证 Manager 与已成功启动的 v3.2.0-legacy 内核能否完成实际 root 授权。

刷机以及root自用教程

发表于 2026-01-13 更新于 2026-01-19

从去年到现在，我入刷机这个圈子也有小一年了，总说从刷机小白变成刷机大佬只需要一次黑砖，但实际上我也是砖了几十次才慢慢了解到其中的各种原理的，现在算是半只脚入了这个门槛了，这篇博客会跟随我以后的刷机经历不断更新的，以后相关的内容都会添在后续。

0.刷机前的必要准备——解锁bootloader

我之前刚开始刷机的时候使用的设备是红米的note7，那时候小米的解锁政策还很松，大部分时候我还是会推荐用小米系的手机来玩机配环境什么的，但是现在国内几大厂商我只推荐魅族和一加，小米在今年元旦的时候在小米社区已经把申请bl相关的模块完全删除找不到了，也就意味着小米发烧时代完全落幕，传统ov以及底下两个子品牌realme和iqoo也是完全没有解锁的渠道（以上说法排除漏洞解锁的情况），一加虽然加了一层申请政策，但是目前申请难度还是比较低的，基本都能解，魅族手机有内置残血root，酷安某贼大佬的煤油工具箱还能提供解锁相关的功能，所以总体门槛不高，刷机搞root的主体现在就以洋垃圾机型以及漏洞机型还有老小米的为主，这里以小米系举例（因为别的牌子我也没用过），老机型就是先给设备绑定账号，然后使用小米官方解锁工具miunlock进行解锁操作，解锁会清空手机数据，需要提前备份好重要数据，新设备能解都是靠漏洞了，这里就不做讨论

Q:为什么要解锁？

A:BL锁是厂商的一种安全机制，bootloader是在手机通电后最先启动的引导程序，负责初始化各种硬件驱动之类的程序，bl锁相当于是对系统的分区和镜像加了一层验证，使其只能加载运行官方签名的系统和分区镜像（比如一会会说到的recovery，还有boot之类的分区镜像），拒绝所有第三方分区和镜像（这就意味着刷机权限锁死，如果用某些方式强刷会因为签名验证不通过导致黑砖，这种很难办），这样大大降低了恶意软件、病毒通过底层系统侵入的风险，保护用户数据和厂商系统的完整性。

*补：新版本一加似乎也加了防回滚熔断机制，不知道具体还好不好刷

1.解锁后的第一步——明确卡刷和线刷的概念

卡刷是在早期普遍有sd卡的时候得名，相当于把刷机包放在存储设备中再接入手机，执行对应的解包和刷机操作，现在不用内存卡了，把刷机包放在内部存储空间也是同理，这是现在手机官方系统更新常用的方式，这里就能引入一个新的概念，那就是recovery模式（恢复模式），这个模式独立于主系统运行，普通用户能使用到的官方recovery一般只有恢复出厂设置这样的选项，来解决没解锁bl情况下的一些黑砖问题，现在的卡刷基本都是用第三方的recovery来完成的

线刷是使用数据线来进行刷入，一般线刷包会包括多个分区文件，得进入fastboot模式进行每个分区的刷入，一般对刷机比较开放的厂商都会有自己的刷机工具（如miflash）或刷机脚本，如果是进9008深刷的话一般用刷机匣等工具（9008概念一会说）

Q:recovery启动的原理以及结构是什么？

A:一般由四个部分组成：精简Linux内核、ramdisk（虚拟内存盘）、recovery主程序、资源文件

系统中的分区结构如下

分区名称 作用
/boot 存放主系统的内核和引导文件。
/system 存放 Android 操作系统本身（UI、应用等）。
/recovery Recovery 专属领地，与 /boot 并列独立。
/data 存放你的照片、微信聊天记录和 App。
/cache 存放系统运行产生的临时垃圾。
/misc 关键桥梁。存放启动标志位（比如：下次开机是进系统还是进 Recovery）。

关于其是如何启动的，正常来说长按电源加音量（上下键可能不同厂商不一样）时，手机会先启动bootloader引导程序，然后检查/misc分区的指令或者判断你物理按键的组合（可能由主板结构决定），如果识别到recovery请求，就不会加载进boot分区，而是直接加载进recovery分区，然后recovery内核启动，最后让屏幕上显示操作菜单

2.找包和载工具

在学习各种刷机包的移植之前，我们很大一部分精力都在不断找包的过程中，这里分享一个某贼的萤火虫资源站：萤火虫资源站

现在网上能找到的基本是卡刷包，得使用recovery来刷，只有像小米那样的官方固件包才有一键刷入脚本或者是线刷大包，当然，也有专门提取卡刷包镜像的工具，镜像提取出来之后就能用fastboot来线刷了

刷机的工具可以直接搜索Androidstudio官方工具包，里面包含两个最常用的工具——adb和fastboot，我们刷机主要就是用这两个

刷机以lineage os为例，首先想刷类原生的官方包，需要先载下他们官方的recovery，用recovery来刷入

4.清除手机数据

这里以twrp为例

如果是lineage os或者一些第三方的类原生的话，使用他们官方的rec，一般情况下使用sideload模式刷机

点击apply update（有时候要在advanced里面enable adb），这会就会进入sideload刷机模式，这时候只需要在电脑上执行以下命令就可以进行刷入

adb sideload 刷机包名/路径.zip

Q:啥是sideload刷机，什么原理？

A:普通的“卡刷”需要你先把 ZIP 包拷贝到手机存储卡中，然后让 Recovery 去读取和安装。而 Sideload 的原理是建立一条直接的数据通道：

PC 端 (Sender)：电脑通过 adb 协议充当发送者，读取本地的 ZIP 文件并将其分块发送。

手机端 (Receiver)：手机进入 Recovery 的 Sideload 模式，充当接收者。它并不把接收到的文件“存”到 SD 卡上（或者只存入临时缓存区），而是直接读取数据流进行解压和安装。

当手机系统崩溃无法开机，且无法连接电脑传输文件到 SD 卡时（无法挂载 MTP 模式），Sideload 是唯一的“卡刷”救命稻草，因为它不需要进入系统，也不依赖 SD 卡的文件系统是否正常。对于不支持外置 SD 卡且内置存储已满，或者数据分区已加密无法读取的情况，Sideload 可以直接从电脑端读取数据。

6.后续操作以及救砖

刷机到这一步，如果能开机的话就算结束了，刷机是很简单的，但是，很多情况下没这么好开机。

刷不带gapp的类原生很多时候会出现网络连接相关的问题，这时候需要在开机前刷入对应安卓版本的gapp包，把谷歌全家桶安排上之后就可以基本解决网络断联问题。

救砖相关的内容，我这里分几种常见情况来说：

1.卡一屏，或者二屏，能进rec：这种情况优先尝试格式化data，先格了看看能不能开机，如果之前刷入的操作都按着包的作者来做的话，格式化完data基本都能开机，如果开不了的话很有可能是包有些问题，比如rec版本不匹配之类的，这时候如果比较着急的话先刷自己手机系统的官方固件，能线刷尽量线刷，如果没线刷包就卡刷，还得注意一下rec版本是否匹配。

2.卡一屏，进不了rec：这种的话可能会直接跳到fastboot页面，可以先尝试重刷一下rec，看看能不能进，能进的话就给它格式化data再看看开不开得了机。如果这种rec也进不去的话，就通过线刷官方包的方式刷回去能救，比如miflash就能刷，如果线刷包没有脚本的话，就手动把几个重要的img镜像给使用fastboot flash指令刷入，再看看能不能开机。

3.卡一屏，进不了fastboot，或者干脆不亮：这种就算是比较严重的砖了，正常刷是遇不到这种情况的，如果你的手机支持物理按键强制进入9008工程模式的话，那就按照官方办法把手机接入电脑，查看9008端口是否启用，有启用的话一般使用某贼大佬开发的刷机匣，导入对应引导文件，刷回救砖包或官方线刷包就能救。如果这种没办法的话，一般建议用支持的9008工程线试试，天玑系列芯片的话也有进入工程模式的方法，原理相同，这里不过多赘述。如果工程模式都进不了的话，那只能是通过拆机短接的方式来进工程模式刷了，但是这种情况没专门的工具不建议自己动手，建议是拿钱消灾了。

Q:什么是9008模式，刷机原理是什么？

A:9008 模式（官方名称为 Qualcomm HS-USB QD-Loader 9008）是高通（Qualcomm）芯片手机特有的一种底层刷机模式，也被称为 EDL 模式（Emergency Download Mode，紧急下载模式）。权限极高：它直接跳过了系统的层层校验，允许电脑向手机的闪存（存储芯片）里直接写入底层镜像文件。普通刷机（如 Fastboot 或 Recovery）运行在手机的二级引导程序或系统分区上。而 9008 模式运行在高通芯片（SoC）固化在硬件里的 PBL (Primary Boot Loader，初级引导程序)。硬件固化：PBL 是一段烧死在芯片只读存储器（ROM）里的代码，无法被用户删除或损坏。启动机制：当手机启动时，如果发现闪存里的引导文件损坏，或者检测到特定的硬件触发信号（如短接 Test Point 或特殊的刷机线），CPU 就会自动进入 9008 模式。此时手机就像一台只有 CPU 和 USB 接口在工作的“裸机”，不依赖闪存里的任何系统。

第一阶段：Sahara 协议 (握手)

手机连接电脑后，会识别为 Qualcomm HS-USB QD-Loader 9008 端口。此时，电脑端软件（如 QFIL 或 MiFlash）通过 Sahara 协议 将一个被称为 Programmer（引导加载程序，通常是 .mbn 或 .elf 文件） 发送到手机的 RAM（内存） 中运行。

关键点： 这个 Programmer 必须经过手机厂商的数字签名验证，否则无法运行。

第二阶段：Firehose 协议 (数据灌输)

一旦 Programmer 在内存中成功运行，它就会启动 Firehose 协议。这是一个基于 XML 指令的通信方式。

电脑发送 XML 指令告诉手机：“请把这个 4GB 的系统镜像写进 UFS/eMMC 闪存的第 X 扇区”。

Programmer 接收指令，直接绕过 Android 系统，将镜像文件精准地“填”进手机的存储分区。

为什么它能“救砖”？

普通刷机就像是给正在运行的房屋（系统）换门窗，如果地基（引导分区）坏了，你就进不去了。
而 9008 刷机相当于施工队直接空降到地基现场：

  1. 完全跳过闪存限制：即使闪存被格式化、分区表丢失，只要 CPU 没坏，就能重写分区。

  2. 不依赖 Bootloader 锁：在许多老旧机型上，9008 模式可以绕过 Bootloader 解锁权限（虽然近年来厂商加强了服务器验证）。

  3. 直接读写物理扇区：它可以对存储芯片进行最底层的擦除和写入。
