某博16.4.0数据包s值逆向（详细版）

发表于 2026-08-14

微博请求参数 s 逆向分析完整复盘

这是一份面向初级逆向工程学习者的实验记录。它记录了本次 Android ARM64 libslib.so 分析从 Java 调用链、JNI、外层 ELF Loader、Frida 动态观察、隐藏 ELF dump、IDA 静态分析，到 Python 独立复现的完整过程。

1. 最终结论

本次目标是还原请求参数 s 的 mode 3 算法。

最终确认的 Java 调用链：

RequestParam.initUserParam
  -> js.a(user.uid)
  -> SLib.newCalculateS(user.uid, 3)
  -> SLib.nativeNewCalculateS(Context, String, int)
  -> 外层 libslib.so
  -> 运行时解包并手工映射隐藏 ELF
  -> 隐藏 ELF 的 JNI_OnLoad
  -> RegisterNatives
  -> 真实 nativeNewCalculateS
  -> calculate_s_mode3

磁盘上的 libslib.so 主要是加载器和完整性检查逻辑，真正的 s 算法在运行时映射的匿名隐藏 ELF 中。

mode 3 的最终算法是：

U = MD5(uid).hexdigest()
S = MD5(secret32).hexdigest()
D = MD5(device_code).hexdigest()

primary = SHA512(S + D + U).hexdigest()
selector = SHA512(D + U).hexdigest()

cursor = 0
result = []
for i in range(8):
    cursor = ord(selector[15 * i + cursor]) & 0x0F
    result.append(primary[15 * i + cursor])

s = "".join(result)

3. 初学者需要先理解的概念

3.1 Java 和 native 的边界

Java 中的 native 方法只有声明，没有 Java 方法体：

private native String nativeNewCalculateS(
        Context context,
        String input,
        int mode
);

真正实现位于 .so 文件中。Java 调 native 的过程需要 JNI 建立映射。

3.2 JNI 静态导出和动态注册

静态导出通常使用长名称：

Java_com_sina_weibo_security_SLib_nativeNewCalculateS

动态注册则在 JNI_OnLoad 中调用 RegisterNatives：

struct JNINativeMethod {
    const char *name;
    const char *signature;
    void *fnPtr;
};

因此，找不到 Java_... 并不代表 native 方法不存在。

3.3 ASLR 和相对偏移

Android 每次启动进程时，绝对地址可能变化：

绝对运行时地址：0x718599fac4
镜像基址：      0x718598d000
相对偏移：      0x12ac4

稳定记录应使用：

relative_offset = runtime_address - image_base

本次真实目标：

mode3                = hidden_image_base + 0x161b4
md5                  = hidden_image_base + 0x2c50c

4. 第一步：从请求参数反推 Java 调用链

逆向时不要一开始就在 native 函数里猜“哪个像加密”。先从业务结果反向追踪。

4.1 找到请求参数 s

在 JADX 中搜索：

曾经看到过这样的反编译结果：

4.2 追踪 mS 的赋值

在 RequestParam.initUserParam() 中找到：

this.mS = com.sina.weibo.utils.js.a(user.uid);

因此 s 的输入来自用户 UID。

4.3 分析 js.a(String)

反编译逻辑可整理为：

public static String a(String uid) {
    synchronized (I) {
        if (TextUtils.equals(uid, G) && !TextUtils.isEmpty(H)) {
            return H;
        }

        if (WeiboApplication.l != null) {
            G = uid;
            H = SLib.getInstance().newCalculateS(uid, 3);
            return H;
        }

        return "";
    }
}

关键结论：

  1. 第一个输入是原始 UID。
  2. mode 固定为 3。
  3. G 保存上一次 UID。
  4. H 保存上一次结果。
  5. 相同 UID 可能直接命中缓存，不再次进入 native。
  6. 需要重启进程、切换 UID 或清空缓存后，才能稳定观察底层调用。

4.4 分析 SLib

    if (sLoadLibrarySuccess && sInit) {

6. 第三步：识别控制流混淆

6.1 混淆的典型表现

在外层和隐藏 ELF 中都看到了：

状态变量反复和常量比较

6.2 初学者常犯错误

错误：把每一个随机常量都当作密钥、魔数或业务参数。

解决：优先标记真实副作用：

  • 系统调用。
  • BL/BLR 调用。
  • 全局变量读写。
  • mmap、mprotect、dlopen、dlsym。
  • 函数指针保存。
  • JNI 函数表调用。
  • 字符串、哈希状态和输出缓冲区。

状态常量通常只是控制流编号。先恢复“做了什么”，再恢复“如何绕路”。

8. 第五步：恢复隐藏 JNI_OnLoad

8.1 为什么要找隐藏 JNI_OnLoad

外层 JNI_OnLoad 只注册了 WBSecurity。真正的 SLib 注册发生在第二层隐藏 ELF 中。

所以要找到：

隐藏 JNI_OnLoad 被解析的位置
隐藏 JNI_OnLoad 被调用的位置

8.2 解析函数地址

在 resolve_unpacked_JNI_OnLoad 中，先解密得到：

JNI_OnLoad\0

随后查找 ELF 符号并计算：

image->jni_onload = image->load_bias + symbol->st_value;

关键汇编：

LDR X15, [X8,#8]       ; Elf64_Sym.st_value
LDUR X17, [X29,#...]   ; load bias
ADD X15, X15, X17
STR X15, [X20,#0x180]  ; 保存隐藏入口

外层关键偏移：

libslib.so + 0x239A8  保存隐藏 JNI_OnLoad
libslib.so + 0x1C7C0  调用隐藏 JNI_OnLoad

调用前的高层逻辑：

callback = unpack_ctx->loaded_image->jni_onload;
if (callback != NULL) {
    return callback(vm, reserved);
}

对应核心指令：

BLR X8

8.3 为什么静态 IDA 看不到算法

因为隐藏 ELF 只有运行时才：

  1. 从 APK 或内存中取得内容。
  2. 在匿名内存中映射。
  3. 完成重定位和依赖解析。
  4. 注册 SLib native 方法。

此时原始 IDB 只能看到 Loader，不能看到真实 nativeNewCalculateS。

9.4 读取 libc++ std::string

本次 ARM64 libc++ 字符串使用短字符串优化和长字符串两种布局。Frida 读取函数：

function readStdString(value) {
    const object = ptr(value);
    const first = object.readU8();
    let size;
    let data;

    if ((first & 1) !== 0) {
        size = Number(object.add(Process.pointerSize)
            .readU64().toString());
        data = object.add(Process.pointerSize * 2).readPointer();
    } else {
        size = first >>> 1;
        data = object.add(1);
    }

    return {
        object: object.toString(),
        data: data.toString(),
        size,
        text: size === 0 ? '' : data.readUtf8String(size)
    };
}

不要把 JNI jstring、C 字符串和 C++ std::string 当成同一种对象。它们的指针和内存布局不同。

10. 第七步：dump 隐藏 ELF

10.1 为什么要 dump 匿名内存

隐藏 ELF 没有正常文件路径，Process.findModuleByAddress() 可能返回空：

moduleName = null
mappingFile = null

但它仍然有匿名映射。必须记录：

  • 起始地址。
  • 结束地址。
  • 权限。
  • 每段的大小。
  • 目标函数所在偏移。
  • 与本次运行对应的 metadata。

10.2 为什么只 dump r-x 不够

算法会读取：

  • 代码段。
  • 只读常量。
  • 哈希初始向量。
  • hex 查找表。
  • GOT 和全局状态。
  • 运行时重定位数据。
  • 尾部 rw- 数据段。

只 dump 可执行段会导致 IDA 中大量：

MEMORY[...]

或出现未映射的全局引用。

dump 时遇到的问题：尾部 rw- 映射不是在代码映射出现时就稳定存在。解决方式：

def build_memory_image(dump_dir, metadata):
    base = int(metadata["reconstructedBase"], 0)
    end = int(metadata["reconstructedEnd"], 0)
    image = bytearray(end - base)

    for memory_range in metadata["ranges"]:
        dump_file = memory_range.get("dumpFile")
        if dump_file is None:
            continue

        range_base = int(memory_range["base"], 0)
        expected_size = int(memory_range["size"])
        data = (dump_dir / dump_file).read_bytes()

        if len(data) != expected_size:
            raise ValueError("dump size mismatch")

        offset = range_base - base
        image[offset:offset + len(data)] = data

    return base, bytes(image)

def make_elf(payload):

        1,  # current ELF version
        0,  # ELFOSABI_NONE

        64,

        0,

        0,

11.3 这个 ELF 的限制

它是分析用合成 ELF，不是原始隐藏 ELF 的完整恢复：

  • 没有恢复原始 section table。
  • 没有完全恢复原始 program header 布局。
  • 文件偏移重新安排。
  • guard page 使用零填充。
  • 反映的是 dump 时刻的自修改状态。

它的目的只有一个：

保持 image offset 不变，让 IDA 能建立代码和数据引用。

11.4 文件偏移计算

合成 ELF 中 payload 从文件偏移 0x1000 开始：

ELF file offset = 0x1000 + image offset
                = 0x1000 + 0x12ac4
                = 0x13ac4

不要把 0x13ac4 和原始 ELF 的真实 file offset 混为一谈。它只是合成文件中的偏移。

13.2 MD5 final 的识别方法

MD5 final 的关键证据：

  1. 读取累计字节数。
  2. 左移 3 位得到 bit length。
  3. 对当前长度 % 64。
  4. 根据是否小于 56 决定补到 56 或 120。
  5. 追加 0x80 和零。
  6. 追加 8 字节长度。
  7. 输出四个 32 位状态，共 16 字节。

典型逻辑：

used = length % 64;
if (used < 56)
    padding = 56 - used;
else
    padding = 120 - used;

bit_length = length * 8;
update(ctx, padding_bytes, padding);
update(ctx, &bit_length, 8);
write_digest_16_bytes(ctx, output);

顺序可以通过动态日志和三处调用点共同确认。最终逻辑中变量命名为：

14. 第十一步：识别 SHA-512

14.1 SHA-512 初始向量

在 0xEA50 附近找到：

按小端解释：

0x6A09E667F3BCC908

这是标准 SHA-512 初始向量。

14.2 四个 __int128 为什么是八个状态

包装函数中：

v69 = v18;
v70 = v17;
v71 = v16;
v72 = v15;

每个 __int128 是 16 字节，四个变量合计：

4 * 16 = 64 bytes = 512 bits = 8 * uint64_t

所以它们就是：

H[0] 到 H[7]

IDA 使用 SIMD 寄存器一次装载两个 64 位值，因此显示成 __int128。

14.3 SHA-512 的三层函数

包装函数：

0x17c54 sha512_update

14.4 128 字节分组证据

在 sha512_update 中看到：

17F18  MOV X0, X21
17F1C  MOV X1, X20
17F20  BL  sha512_compress_block
17F24  MOV W9, #0xEE62

17F2C  SUB X19, X19, #0x80

这直接说明：

while (size >= 128) {
    sha512_compress_block(ctx, data);
    data += 128;
    size -= 128;
}

SHA-512 的分组大小是 128 字节。

14.5 80 轮压缩证据

在 sha512_compress_block 中搜索：

CMP W9, #0x50

0x50 = 80，说明循环计数器走 80 轮。这和 SHA-512 标准一致。

14.6 64 字节输出证据

在 sha512_final 的 0x1814c-0x183ec，连续把八个 64 位状态按大端序拆成 64 个字节：

LDR X8, [X20,#0x10]
LSR X8, X8, #0x28
STRB W8, [X19,#2]
...
LDR X8, [X20,#0x48]
STRB W8, [X19,#0x3F]

计算：

8 个状态 * 8 字节 = 64 字节

所以 sha512_digest 的输出就是标准 64 字节摘要。

14.7 SHA-512 padding

sha512_final 中：

AND X24, X8, #0x7F  ; length % 128
CMP X24, #0x70      ; 比较 112

如果当前长度小于 112，就补到 112；否则补到 240，然后追加 16 字节 bit length：

BL sha512_update    ; padding
MOV W2, #0x10
BL sha512_update    ; 16-byte length

这也是 SHA-512 的标准收尾结构。

15. 第十二步：识别小写 hex 转换

15.1 hex 表

在 0xEA90 找到：

15.2 std_string_push_back_char 不是混淆函数

0x32c50 的汇编：

ADRP X16, #0x37410@PAGE
LDR  X17, [X16,#0x37410@PAGEOFF]
ADD  X16, X16, #0x37410@PAGEOFF
BR   X17

这是 GOT 间接跳板，不是算法混淆。真实函数地址由运行时重定位填入 0x37410，当前静态 dump 中可能是 0。

判断方法：

只有 ADRP/LDR/ADD/BR，没有循环和算法运算 -> thunk 或导入跳板

调用点中：

X0 = std::string*
W1 = 一个字符

且每个 digest 字节调用两次，因此可以高置信度命名为：

std_string_push_back_char

15.3 高低半字节

mode 3 的 hex 循环关键指令：

BL  std_string_push_back_char

LDRB W1, [X8]       ; hex_table[byte & 0x0F]
BL  std_string_push_back_char

等价于：

high = byte >> 4;
low = byte & 0x0F;
output.push_back(hex_table[high]);
output.push_back(hex_table[low]);

17. 第十四步：恢复最终 8 轮选择算法

17.1 循环计数

关键位置：

16E7C  CMP W8, #8

说明循环执行 8 轮。

17.2 计算 15 * round

关键指令：

16ED0  LSL W16, W8, #4
16ED4  SUB W16, W16, W8

等价于：

base = (round << 4) - round;
base = 16 * round - round;
base = 15 * round;

17.3 使用 selector 更新 cursor

逻辑可整理成：

selector_index = 15 * round + cursor;
selector_byte = selector_hex[selector_index];
cursor = selector_byte & 0x0F;

因为 selector 已经是 ASCII hex 字符，所以：

ASCII('1') & 0x0f = 1
ASCII('a') & 0x0f = 1
ASCII('9') & 0x0f = 9
ASCII('f') & 0x0f = 6

17.4 从 primary 取字符

primary_index = 15 * round + cursor;
result[round] = primary_hex[primary_index];

关键写入：

16EEC  LDRB W16, [X13,W16,SXTW]
16EEC  STRB W16, [X20,W8,SXTW]

这说明每轮取一个字符写入最终 8 字节输出。

18. Python 独立复现

完整文件是当前目录的 calculate_s.py：

#!/usr/bin/env python3
import argparse
import hashlib


def md5_hex(value: str) -> str:
    return hashlib.md5(value.encode("utf-8")).hexdigest()


def calculate_s(uid: str, secret32: str, device_code: str) -> str:
    uid_md5 = md5_hex(uid)
    secret_md5 = md5_hex(secret32)
    device_md5 = md5_hex(device_code)

    primary = hashlib.sha512(
        (secret_md5 + device_md5 + uid_md5).encode("ascii")
    ).hexdigest()

    selector = hashlib.sha512(
        (device_md5 + uid_md5).encode("ascii")
    ).hexdigest()

    cursor = 0
    result = []
    for round_index in range(8):
        cursor = ord(selector[15 * round_index + cursor]) & 0x0F
        result.append(primary[15 * round_index + cursor])

    return "".join(result)


def main() -> None:
    parser = argparse.ArgumentParser()
    parser.add_argument("uid")
    parser.add_argument("secret32")
    parser.add_argument("device_code")
    args = parser.parse_args()
    print(calculate_s(args.uid, args.secret32, args.device_code))


if __name__ == "__main__":
    main()

20. 本次犯过的错误和解决办法

20.1 把 WBSecurity 当成 s 算法

错误原因：看到 security、signature 等名字就直接联想到请求签名。

解决：回到 Java 调用链，确认 s 来自 SLib.newCalculateS(uid, 3)；WBSecurity 只是外层解包/完整性检测。

20.2 在外层 IDB 中盲目寻找算法

错误原因：认为所有代码都应该在磁盘上的 libslib.so 中。

解决：看到 APK/ZIP 读取、ELF 解析、mmap、mprotect、dlopen、dlsym 后，确认这是 Loader，转向动态 dump 隐藏 ELF。

20.3 把随机状态常量当成密钥

错误原因：混淆伪代码中出现很多十六进制常量。

解决：先追踪真实副作用和数据读写，忽略状态编号；哈希初始向量、输出缓冲区和真实调用比随机状态常量更有价值。

20.4 忽略 Java 缓存

错误原因：重复调用相同 UID，却发现 native hook 不再触发。

解决：识别 js.a 的 G/H 缓存；重启进程、换 UID 或清空缓存。

20.5 Frida server 重复启动

错误现象：

Address already in use

解决：先检查已有 server PID 和端口，不要重复启动；必要时结束旧实例，再启动一个版本匹配的 server。

20.6 把 spawn 超时直接判断为反调试

错误原因：完整脚本失败时没有先做最小探针。

解决：按 ADB、server、版本、端口、最小 spawn、脚本 API 的层次逐步排查。最终确认是旧 server 会话状态问题，没有证据证明是应用反调试。

20.7 使用了不兼容的 Frida API 形式

错误表现：attachModuleObserver 不可用、enumerateRangesSync 参数差异、匿名 range 的 file 字段异常。

解决：增加轮询 fallback、兼容两种 enumerateRangesSync 参数、使用 range.file == null。

20.8 只 dump r-x 段

错误原因：认为代码段就是全部算法。

解决：补 dump rwx、rw- 和尾部数据段，同时保存 metadata。否则全局数据、GOT、查找表和重定位引用不完整。

20.9 dump 时机太早或固定等待

错误原因：固定等待几秒后只 dump 一次。

解决：使用 RegisterNatives 和第一次真实 nativeNewCalculateS 作为同步点，并在函数返回后重新检查 maps，补抓延迟出现的数据段。

20.10 混用了不同运行的 dump

错误原因：不同运行的绝对地址都看起来像隐藏 ELF，直接拼接或交叉使用。

解决：每轮保存自己的 payload_metadata.json、nativeNewCalculateS.json 和对应 dump；只使用同一轮 metadata 指向的段。

20.11 把自修改 trampoline 当作真实函数体

错误现象：目标入口只有几条 LDR/BR，IDA 函数体看起来不完整。

解决：对比运行前后字节，使用 prepatch 快照恢复入口，并在 IDA 中重新定义 calculate_s_mode3。

20.12 把 sub_32C50 当成混淆函数

错误原因：函数名未知且调用位置在混淆代码中。

解决：看到它只有 ADRP/LDR/ADD/BR，判断为 GOT thunk；结合 X0=std::string*、W1=char 和调用效果，命名为 std_string_push_back_char。

20.13 忽略 SHA-512 的第 4 个参数

错误原因：IDA 伪代码中的 v3 看起来像未初始化局部变量。

解决：回看函数入口和调用约定。ARM64 的第 4 个整数参数在 W3，调用点明确执行 MOV W3, WZR，因此修正原型为四参数。

20.14 把 TPIDR_EL0 + 0x28 当成摘要状态

错误原因：它出现在函数开头，并参与后面的比较。

解决：识别 ARM64 stack canary：

MRS X8, TPIDR_EL0
LDR X8, [X8,#0x28]
STR X8, [stack]

函数结尾再次读取并比较，这是栈保护，不是 64 字节哈希分组。

20.15 混淆了不同样本的结果

错误原因：早期记录中有 2032848787248 -> 5feb09b6，最终日志是 8225577424 -> 317bb874。

解决：给每个样本保存独立输入、日志和输出。本文明确以最终样本为主。

21. IDA 中识别常见算法的方法

21.1 识别 MD5

搜索标准初始向量：

01 23 45 67 89 ab cd ef fe dc ba 98 76 54 32 10

再检查：

  • 64 字节分组。
  • 四个 32 位状态。
  • 0x80 padding。
  • 64 位 bit length。
  • 16 字节输出。

21.2 识别 SHA-512

搜索：

08 C9 BC F3 67 E6 09 6A
3B A7 CA 84 85 AE 67 BB

再检查：

  • 128 字节分组。
  • 八个 64 位状态。
  • 80 轮。
  • 16 字节长度字段。
  • 64 字节大端输出。

21.3 识别 hex 转换

寻找：

0123456789abcdef

或观察：

LSR reg, #4
AND reg, #0xF

再看是否每个输入字节产生两个输出字符。

21.4 识别字符串拼接

关注：

  • 读取两个字符串长度。
  • 计算长度和。
  • 目标容量检查。
  • 两段连续复制。
  • 末尾写零。

不要只依赖函数名，因为 libc++ 符号可能被裁剪或通过 GOT 间接调用。

2. 需要先了解的几个概念

2.1 JNI 是什么

JNI 是 Java/Kotlin 调用 C/C++ 代码的桥梁。例如 Java 中出现：

private native String nativeNewCalculateS(
        Context context,
        String input,
        int mode
);

这个方法只有声明，没有 Java 方法体。实际实现位于某个 native 库中。

2.2 JNI 方法如何与 native 函数对应

常见方式有两种。

静态导出

native 函数名称遵循固定格式，例如：

Java_com_sina_weibo_security_SLib_nativeNewCalculateS

这种情况通常可以直接在 IDA 的导出函数或 Functions 窗口中搜索 Java_。

动态注册

so 在 JNI_OnLoad 中调用 RegisterNatives，使用一张表建立 Java 方法和 native 函数的对应关系：

static JNINativeMethod methods[] = {
    {
        "nativeNewCalculateS",
        "(Landroid/content/Context;Ljava/lang/String;I)Ljava/lang/String;",
        native_new_calculate_s
    }
};

动态注册时，函数名可以完全被去掉。分析重点会变成：

JNI_OnLoad -> FindClass -> RegisterNatives -> JNINativeMethod 表

2.3 JNI_OnLoad 是什么

Android 加载 so 后，通常会调用导出的 JNI_OnLoad：

jint JNI_OnLoad(JavaVM *vm, void *reserved);

开发者经常在这里：

  • 获取 JNIEnv。
  • 查找 Java 类。
  • 动态注册 native 方法。
  • 初始化全局状态。
  • 解密字符串或代码。
  • 加载第二层 so。

因此，找 native 调用链时，JNI_OnLoad 通常是第一个重要入口。

2.4 什么是手工 ELF Loader

正常情况下，Android 的 linker 负责加载 so。手工 ELF Loader 会自己完成类似工作：

  1. 读取 ELF Header。
  2. 解析 Program Header。
  3. 计算映射地址和 load bias。
  4. 使用 mmap 映射 PT_LOAD 段。
  5. 复制文件内容和清零 BSS。
  6. 使用 mprotect 设置 r-x、rw- 等权限。
  7. 解析动态表、依赖库和重定位。
  8. 查找并调用隐藏 ELF 的 JNI_OnLoad。

如果一个 so 同时出现大量 ELF 解析逻辑、mmap、mprotect、dlopen、dlsym，就要怀疑它在加载另一个 ELF。

3. 第一步：先在 Java 层把范围缩小

不要一开始就在几百个 native 函数中猜测。先确认 Java 到 native 的精确边界。

3.1 找到请求参数写入点

在 RequestParam.fillCommonParam() 中看到：

bundle.putString("s", getS());

原 APK 因常量复用，反编译结果一度显示为：

bundle.putString(com.hpplay.soap.a.m, getS());

继续查看 com.hpplay.soap.a.m，可以确认其值就是：

public static final String m = "s";

这是一个常见反编译现象：不同库中的相同字符串常量可能被 JADX 显示成一个意外的字段引用。不要只看字段名，要继续确认字段的实际值。

3.2 追踪 mS 的赋值

RequestParam.initUserParam() 中存在：

this.mS = com.sina.weibo.utils.js.a(user.uid);

所以 Java 层的输入是当前用户的 uid。

3.3 分析 js.a(String)

目标方法的核心逻辑可以整理成：

public static String a(String uid) {
    synchronized (I) {
        if (TextUtils.equals(uid, G) && !TextUtils.isEmpty(H)) {
            return H;
        }

        if (WeiboApplication.l != null) {
            G = uid;
            H = SLib.getInstance().newCalculateS(uid, 3);
            return H;
        }

        return "";
    }
}

可以得出：

  • 第一个参数是原始 uid，Java 层没有拼接或哈希。
  • 第二个参数固定为 3。
  • G 保存缓存对应的 UID。
  • H 保存计算结果。
  • 相同 UID 会直接返回缓存。
  • js.b() 会把 H 清空，使缓存失效。

3.4 确认真正的 native 声明

SLib 中存在：

private native String nativeNewCalculateS(
        Context context,
        String input,
        int mode
);

public String newCalculateS(String input, int mode) {
    if (sLoadLibrarySuccess && sInit) {
        return nativeNewCalculateS(this.mAppContext, input, mode);
    }
    return null;
}

同时静态初始化中加载：

System.loadLibrary("slib");

到这里，Java 层已经完成收口：

目标库：libslib.so
目标类：com.sina.weibo.security.SLib
目标方法：nativeNewCalculateS(Context, String, int)
实际输入：uid
mode：3

这比直接在 IDA 中搜索“像加密的函数”可靠得多。

4. 第二步：在 IDA 中检查 JNI 注册方式

4.1 先搜索最直接的特征

  • 找不到 Java_com_sina_...nativeNewCalculateS。
  • 找不到 nativeNewCalculateS 明文。
  • 找不到 SLib 类名明文。
  • 只能找到 com/sina/weibo/security/WBSecurity。

这意味着至少存在一种情况：

  1. SLib 使用动态注册，并且注册表被加密。
  2. SLib 的真实实现位于另一个运行时加载的模块中。
  3. JNI 方法名和类名在运行时才生成。

4.2 分析可见的 WBSecurity 注册表

JNI_OnLoad 中可以看到：

FindClass("com/sina/weibo/security/WBSecurity")
RegisterNatives(..., table, 3)

注册表位于 0x38C80，包含三个方法：

isUnpackSuccess  ()Z
getUnPackResult  ()Ljava/lang/String;
getTimeCost      ()Ljava/lang/String;

这些名称本身就是重要提示：

  • isUnpackSuccess
  • getUnPackResult
  • getTimeCost

一个普通签名算法库通常没有必要向 Java 暴露“解包是否成功”和“解包耗时”。这强烈说明当前库包含解包过程。

4.3 为什么不能把 WBSecurity.getSignature 当成 s 算法

Java 中还有：

WBSecurity.getInstance().getSignature("weibo");

但它位于 so 完整性检测流程中，用来确认 slib 是否正确加载和执行。它和请求参数 s 的链路不同。

判断时应以调用关系为准：

请求 s：RequestParam -> js.a(uid) -> SLib.newCalculateS

完整性检测：WBSecurity.startCheck -> getSignature("weibo")

名字相似不等于用途相同。

5. 第三步：识别控制流混淆

5.1 看到的典型现象

JNI_OnLoad 和多个关键函数具有以下特征：

  • 大量看似随机的 32 位常量。
  • 多层 while 和 switch 风格分发。
  • 一个状态变量不断与随机常量比较。
  • 简单业务动作被大量条件跳转包围。
  • 反编译代码远比实际逻辑复杂。
  • 存在永真或永假的混淆条件。

例如真实逻辑可能只是：

if (callback != NULL) {
    return callback(vm, reserved);
}

经过控制流扁平化后，会变成数十个状态和循环。

5.2 不要逐行解释随机状态常量

初学者很容易陷入逐个解释这些常量：

0x233025B8
0x3D265081
0x2DFC6514

大部分常量只是控制流状态编号，不是算法密钥。

更有效的方法是先标记有真实副作用的指令：

  • 调用系统函数。
  • 读取或写入全局变量。
  • 内存分配和映射。
  • 字符串解密。
  • 间接函数调用 BLR Xn。
  • 保存函数指针。
  • JNI 函数表调用。

然后围绕这些动作恢复高层逻辑。

8.1 解密 JNI_OnLoad 字符串

resolve_unpacked_JNI_OnLoad 中存在一个 11 字节异或循环，结果是：

JNI_OnLoad\0

字符串不是直接存放在 .rodata 中，而是在运行时写入缓冲区。这解释了为什么最初的字符串搜索找不到隐藏入口。

8.2 计算隐藏入口地址

0x23998 附近的 ARM64 指令核心是：

LDR X15, [X8,#8]       ; symbol st_value
LDUR X17, [X29,#...]   ; load bias
ADD X15, X15, X17      ; runtime address
STR X15, [X20,#0x180]  ; 保存隐藏 JNI_OnLoad

等价于：

image->jni_onload = image->load_bias + symbol->st_value;

关键保存位置：

libslib.so + 0x239A8

执行这条指令后：

  • X15 是隐藏 ELF 的真实 JNI_OnLoad 地址。
  • X20 是隐藏 ELF 镜像对象。
  • [X20 + 0x180] 保存该入口。

8.3 调用隐藏 JNI_OnLoad

外层函数 call_unpacked_JNI_OnLoad 的核心逻辑是：

callback = unpack_ctx->loaded_image->jni_onload;
if (callback != NULL) {
    return callback(vm, reserved);
}

关键间接调用位置：

libslib.so + 0x1C7C0

对应 ARM64 指令为：

BLR X8

执行前：

  • X8 是隐藏 JNI_OnLoad 地址。
  • X0 是 JavaVM *。
  • X1 是 reserved。

9. 为什么分析到这个阶段时 IDB 里还没有 s 算法

这一阶段，IDA 分析的还是磁盘上的外层 libslib.so。

但隐藏 ELF 只有在运行时才会：

  1. 从文件中定位或提取。
  2. 分配匿名内存。
  3. 将各个 ELF 段映射到内存。
  4. 执行重定位。
  5. 设置最终内存权限。
  6. 调用隐藏 JNI_OnLoad。

因此，当前 IDB 能看到加载器，却看不到隐藏 ELF 注册的：

nativeInit
nativeNewCalculateS
nativeCheck
nativeGetCheckErr
nativeGetCheckErrType
nativeGetPkgTimeCost
nativeGetV1TimeCost
nativeGetV2TimeCost

这时继续在当前 IDB 中盲目寻找“加密函数”不会得到真实算法。

正确方向是：

动态运行 -> 等待隐藏 ELF 映射完成 -> 获取入口/映射范围 -> dump -> 重新导入 IDA

10. 动态恢复时应该观察什么

10.1 推荐断点一：隐藏入口刚刚解析完成

模块基址 + 0x239A8

断下后记录：

X15                     隐藏 JNI_OnLoad 地址
X20                     隐藏镜像对象
[X20 + 0x180]           保存后的隐藏 JNI_OnLoad

这个位置适合确定隐藏代码位于哪个匿名内存映射。

10.2 推荐断点二：调用隐藏 JNI_OnLoad 前

模块基址 + 0x1C7C0

断下后记录：

X8                      即将调用的隐藏 JNI_OnLoad

此时隐藏 ELF 已经完成主要映射和链接，适合 dump。

10.3 同时观察 RegisterNatives

隐藏 JNI_OnLoad 很可能会调用 RegisterNatives 注册 SLib 方法。

动态记录每个 JNINativeMethod：

struct JNINativeMethod {
    const char *name;
    const char *signature;
    void *fnPtr;
};

ARM64 下每项通常占 24 字节：

+0x00  name
+0x08  signature
+0x10  fnPtr

找到下面这项后即可获得算法入口：

name      = nativeNewCalculateS
signature = (Landroid/content/Context;Ljava/lang/String;I)Ljava/lang/String;
fnPtr     = 真实 native 函数地址

记录 fnPtr 所在映射及相对偏移，然后在 dump 后的镜像中定位。

10.4 为什么 RegisterNatives 比猜函数更可靠

隐藏 ELF 可能仍然存在：

  • 符号表被删除。
  • 函数名被混淆。
  • 控制流平坦化。
  • 字符串被加密。

但只要 Java 能调用 native 方法，运行时就必须建立 Java 方法到函数地址的映射。RegisterNatives 是最直接的事实来源。

11. Dump 后重新导入 IDA 的基本流程

获得隐藏映射后：

  1. 记录每个映射段的起始地址、结束地址和权限。
  2. dump r--、r-x、rw- 等相关段。
  3. 记录隐藏 JNI_OnLoad 和 nativeNewCalculateS 的运行时地址。
  4. 尽量修复 ELF Header 和 Program Header。
  5. 将修复后的 ELF 作为新文件导入 IDA。
  6. 计算运行时地址对应的文件内偏移或相对虚拟地址。
  7. 在新 IDB 中定位 nativeNewCalculateS。
  8. 从 JNI 参数转换开始分析：
GetStringUTFChars
GetStringChars
GetObjectClass
GetMethodID
CallObjectMethod
NewStringUTF
  1. 继续追踪输入 UID、mode 以及设备/包环境数据。

12. 常见误区

12.1 看到 MD5、SHA 就认为找到了算法

签名算法可能调用哈希，但哈希函数只是一个组成部分。必须确认它位于：

nativeNewCalculateS -> ... -> hash

而不是日志、文件校验、插件验签或其他无关流程。

12.2 只按函数名判断用途

getSignature、sign、security 看起来都很可疑，但名字不能替代调用链。

本次 WBSecurity.getSignature("weibo") 就属于完整性检查，而不是请求参数 s 的直接生成链。

12.3 把混淆状态常量当成密钥

控制流扁平化中的随机整数通常只是状态编号。优先关注真正的数据运算和系统调用。

12.4 认为 IDA 没找到函数就是 so 中不存在

还可能是：

  • 动态注册。
  • 字符串运行时解密。
  • 函数位于第二层 ELF。
  • 代码运行时解压。
  • 函数通过间接调用进入。

12.5 只 dump 可执行段

算法可能依赖：

  • 只读常量。
  • 动态字符串。
  • 查找表。
  • 全局状态。
  • 重定位后的 GOT。

只 dump r-x 代码段可能不足以恢复可分析的 ELF，应同时保存相关 r-- 和 rw- 段及映射信息。

12.6 忽略 Java 层缓存

js.a(uid) 会缓存 s。如果只 hook 底层计算函数，第二次相同 UID 请求可能不会再次进入 native。

动态观察时可以：

  • 重启进程。
  • 切换 UID。
  • 调用 js.b() 清空结果缓存。
  • 同时 hook Java wrapper 和 native 边界。

13. 可复用的识别清单

以后遇到类似 so，可以按下面顺序排查。

Java 层

  • 找到参数最终写入请求的位置。
  • 追踪字段的所有赋值点。
  • 确认 native 方法完整签名。
  • 确认输入参数是否经过预处理。
  • 确认是否存在缓存和短路返回。
  • 确认加载的 so 名称。

JNI 层

  • 搜索 Java_ 静态导出。
  • 搜索 JNI_OnLoad。
  • 搜索 RegisterNatives。
  • 搜索 Java 类路径字符串。
  • 检查 JNINativeMethod 三元组。
  • 检查方法名是否运行时解密。

壳和自定义 Loader

  • 是否读取 APK、split APK 或自身 so。
  • 是否出现 ZIP 读取函数。
  • 是否出现 ELF Header / Program Header 解析。
  • 是否调用 mmap、mprotect。
  • 是否调用 dlopen、dlsym。
  • 是否计算 load bias。
  • 是否解析 PT_LOAD、动态表和重定位。
  • 是否再次查找并调用 JNI_OnLoad。
  • 是否存在 unpack、pre-link、load_so 等解密字符串。

动态恢复

  • 在隐藏入口解析后记录入口地址。
  • 保存 /proc/<pid>/maps。
  • dump 所有关联映射段。
  • hook RegisterNatives 获取真实函数地址。
  • 记录运行时基址和函数相对偏移。
  • 将 dump 修复后重新导入 IDA。

14. 静态加载链阶段的最短总结

整个发现过程不是从某个“神秘加密函数”开始，而是逐层用证据缩小范围：

抓包看到 s
  -> Java 找到 bundle.putString("s", getS())
  -> 找到 mS = js.a(uid)
  -> 找到 SLib.newCalculateS(uid, 3)
  -> 找到 nativeNewCalculateS 声明和 libslib.so
  -> IDA 中找不到 SLib 注册表
  -> JNI_OnLoad 只注册 WBSecurity unpack 检测方法
  -> 发现 ZIP + ELF + mmap + mprotect + dlopen + dlsym
  -> 解出 unpack / pre-link / JNI_OnLoad 字符串
  -> 确认存在手工 ELF Loader
  -> 定位隐藏 JNI_OnLoad 保存点 0x239A8
  -> 定位隐藏 JNI_OnLoad 调用点 0x1C7C0
  -> 得出必须动态 dump 隐藏 ELF 的结论

面对复杂混淆时，最有效的原则是：

先确认数据流，再确认调用边界；
先找真实副作用，再处理控制流；
先证明存在第二层代码，再决定是否继续静态分析。

15. 动态分析前必须理解的地址知识

前面的静态分析只告诉我们“应该在哪里观察”。真正运行后，会出现很多不同形式的地址。初学者最容易在这里混淆。

15.1 绝对运行时地址

进程实际运行时看到的地址，例如：

隐藏镜像基址                 0x718598d000
nativeNewCalculateS         0x718599fac4

这类地址受 ASLR 影响。每次重新启动应用，前面的高位地址通常都会变化。

因此，下面这种记录方式不够稳定：

函数地址是 0x718599fac4

更有价值的是记录函数相对镜像基址的偏移。

15.2 相对偏移

计算公式：

函数相对偏移 = 函数运行时地址 - 镜像运行时基址

代入本次数据：

0x718599fac4 - 0x718598d000 = 0x12ac4

因此稳定结论是：

nativeNewCalculateS = hidden_image_base + 0x12ac4

后续运行中虽然绝对地址变化了，但 0x12ac4 一直不变。这说明镜像定位正确。

15.3 模块基址、匿名映射基址和 image base

正常 so 会在 /proc/<pid>/maps 中显示文件路径，例如：

... r-xp ... /data/app/.../lib/arm64/libslib.so

隐藏 ELF 是手工映射的，所以通常只显示：

718598d000-718599f000 r-xp 00000000 00:00 0

它没有文件名，因此 Frida 的 Process.findModuleByAddress() 会返回空。这时需要记录：

  • 绝对运行时地址。
  • 所在匿名映射的起始地址。
  • 整个隐藏镜像的重建基址。
  • 相对匿名映射基址的偏移。
  • 相对重建 image base 的偏移。

15.4 load bias

正常 ELF 中：

运行时地址 = ELF 虚拟地址 + load bias

原始隐藏 ELF Header 没有直接保留在最终代码映射中，所以原始 load bias 不能只靠最终内存字段可靠读取。重建脚本采用：

合成 ELF 的 PT_LOAD.p_vaddr = 0

于是合成 ELF 中：

reconstructed load bias = runtime image base

这是一种为了方便 IDA 加载而采用的明确约定，不应误写成“已恢复原文件的全部 ELF 布局”。

15.5 文件偏移与虚拟地址偏移

重建 ELF 把内存镜像放在文件偏移 0x1000，因此：

目标 ELF 文件偏移
  = payload 文件偏移 + 目标 image offset
  = 0x1000 + 0x12ac4
  = 0x13ac4

本次最终记录：

项目 值
运行时 image base 0x718598d000
运行时 image end 0x71859ca000
完整内存跨度 249856 字节
native 运行时地址 0x718599fac4
native image offset 0x12ac4
合成 ELF 文件偏移 0x13ac4

16. Frida spawn 超时是怎样解决的

16.1 最初的现象

使用：

frida -U -f com.sina.weibo -l ".\frida_dump_slib_payload.js"

出现：

Failed to spawn: unexpectedly timed out while waiting for signal from process

错误中曾出现 usap64 PID，所以一开始可能怀疑 Android USAP 或应用主动干扰。

16.2 不要先猜，先拆分变量

诊断顺序如下：

  1. 检查主机 Frida 版本。
  2. 检查设备端 server 文件版本。
  3. 检查 27042 端口是否已有实例。
  4. 检查现存 server PID、父进程和启动参数。
  5. 用最小 Frida 脚本测试 spawn。
  6. 最小脚本成功后再加载完整 dumper。

实际确认：

主机 Frida       16.1.8
设备 frd1618     16.1.8
设备 ABI         arm64-v8a
Android          13 / API 33
USAP 配置        false

直接执行：

adb shell su -c "/data/local/tmp/frd1618 --version"

最初得到的却是：

Address already in use

原因是设备上已经有一个 server 占用 27042。该命令是在尝试启动第二个实例，并没有证明当前正在工作的 server 版本。

16.3 干净重启 server

找到旧 server PID 后，终止旧实例，再直接读取文件版本并重新启动：

adb shell "su -c 'kill -9 SERVER_PID'"
adb shell "su -c '/data/local/tmp/frd1618 --version'"
adb shell "su -c '/data/local/tmp/frd1618 >/data/local/tmp/frd1618.log 2>&1 &'"
frida-ps -Uai

随后使用最小探针：

frida -U -f com.sina.weibo -q -t 8 `
  -e "console.log('[probe] injected pid=' + Process.id);"

得到：

Spawned `com.sina.weibo`. Resuming main thread!
[probe] injected pid=30686

因此这次 spawn 超时的直接原因是旧 server 会话状态异常，而不是已经证实的应用反调试。

16.4 可复用经验

遇到复杂脚本失败时，先测试：

设备连接 -> server -> 最小 spawn -> 简单 JS -> 完整脚本

不要把“完整脚本执行失败”和“Frida 无法注入”混成一个问题。

17. Frida 16.1.8 脚本兼容问题

17.1 模块观察器不可用

运行时输出：

module observer unavailable; falling back to polling

说明当前 Frida JavaScript 环境没有可用的 Process.attachModuleObserver()。脚本因此使用高频轮询：

const timer = setInterval(function () {
    const module = Process.findModuleByName('libslib.so');
    if (module !== null) {
        clearInterval(timer);
        installLoaderHooks(module);
    }
}, 1);

17.2 enumerateRangesSync 参数形式

Frida 16.x 优先使用：

Process.enumerateRangesSync('r-x');

较新 API 还可能接受 options object。脚本同时保留两种形式作为兼容处理。

17.3 匿名 range 没有 file 字段

匿名映射可能不是：

range.file === null

而是：

range.file === undefined

因此判断应写成：

range.file == null

否则读取 range.file.path 会触发：

TypeError: cannot read property 'path' of undefined

17.4 /proc/self/maps 可能包含非 UTF-8 路径

直接调用 File.readLine() 曾出现：

can't decode byte 0xff

最终脚本改成读取原始字节，只解析地址和权限所需的 ASCII 部分。

17.5 dump 时机比固定延迟更可靠

隐藏镜像的尾部 rw- 数据段并不是与代码段同时稳定出现。固定等待 1 秒或 3 秒都依赖设备启动速度。

更可靠的同步点是：

nativeNewCalculateS 第一次真实调用

因为此时 JNI 注册已经完成，算法即将使用自己的代码和全局数据。

不过本次还观察到：部分尾部数据映射在 Frida onLeave 回调返回后才完全稳定。因此最终又通过实时 /proc/<pid>/maps 确认地址，并补抓两个数据段。

这说明“函数已经返回”与“所有辅助线程/延迟映射都已稳定”不是完全相同的概念。

18. 如何 hook RegisterNatives

18.1 为什么要 hook 它

隐藏 ELF 没有可用符号名，但 Java 要调用 native，就必须把方法名、签名和函数指针交给 ART。

因此 RegisterNatives 是运行时的真实答案。

18.2 JNIEnv 函数表

JNIEnv * 本质上指向一张 JNI 函数表。当前 Android ARM64 环境中，RegisterNatives 位于索引 215：

const env = Java.vm.getEnv();
const table = env.handle.readPointer();
const registerNatives = table
    .add(215 * Process.pointerSize)
    .readPointer();

18.3 ARM64 下的 JNINativeMethod

结构体为：

struct JNINativeMethod {
    const char *name;
    const char *signature;
    void *fnPtr;
};

ARM64 指针是 8 字节，所以一项占：

8 + 8 + 8 = 24 字节

遍历方式：

const entry = methods.add(i * Process.pointerSize * 3);
const name = entry.readPointer().readCString();
const signature = entry.add(8).readPointer().readCString();
const fn = entry.add(16).readPointer();

19. 隐藏镜像的完整 dump

19.1 为什么只 dump r-x 不够

算法代码会访问全局指针、常量、状态和动态字符串。本次 JNI wrapper 会读取：

imageBase + 0x3c750

这个位置不在主 r-x 代码范围，而在后面的 rw- 数据映射中。

如果只保留可执行段：

  • IDA 可以看到部分指令。
  • 全局指针会落到未映射地址。
  • 交叉引用不完整。
  • 反编译结果容易出现大量 MEMORY[...]。

19.2 最终保存的范围

完整样本位于：

slib-dump-complete/

保存的主要范围包括：

image offset 大小 权限 作用
0x00000 73728 r-x 代码
0x12000 4096 rwx 运行时可修改代码页
0x13000 20480 r-x 代码
0x18000 8192 rwx 运行时可修改代码页
0x1a000 102400 r-x 代码和常量
0x36000 8192 rw- 尾部数据
0x3b000 8192 rw- 全局状态和字符串

中间没有读取权限的 guard page 在重建镜像中用零填充，保持所有虚拟偏移不变。

19.3 自修改 JNI wrapper

在较早时刻，nativeNewCalculateS wrapper 的核心形式为：

ADRP X8, global_state_slot
MOV  X1, X0
LDR  X8, [X8, ...]
MOV  X0, X8
B    hidden_calculateS_dispatch

它完成参数重排：

原 JNI 参数：env, thiz, context, input, mode
内部参数：  state, env, context, input, mode

运行后，这个 RWX stub 会被改写成类似：

LDR X16, =TARGET
BR  X16

因此在不同 dump 时刻观察同一个偏移，可能得到不同字节。遇到这种情况，不要立即判断 dump 错误，应考虑自修改代码或运行时 trampoline。

20. 如何重建可载入 IDA 的 ELF

20.1 为什么要包装 ELF

dump 得到的是多个内存片段，不一定包含完整原始 ELF Header。IDA 直接打开平坦二进制时，需要手工选择处理器、基址和段属性。

为了让导入更简单，rebuild_slib_payload.py 创建一个最小 ARM64 ELF64：

  • e_type = ET_DYN。
  • e_machine = EM_AARCH64。
  • 创建一个 PT_LOAD。
  • p_vaddr = 0。
  • payload 文件偏移为 0x1000。
  • 保持所有 runtime image offset 不变。

20.2 重建命令

python ".\rebuild_slib_payload.py" `
  ".\slib-dump-complete" `
  --output ".\slib-dump-complete\libslib_payload_rebuilt.so"

最终产物：

slib-dump-complete/libslib_payload_rebuilt.so

最终 SHA-256：

7a912a1f9981ee28e4da5560a8c544cc2ee2f209348744fdca53343815599506

20.3 重建文件的限制

它是分析用途的合成 ELF，不等同于原始隐藏 ELF 文件：

  • 原始 section table 没有恢复。
  • 原始 program header 数量和权限没有完全恢复。
  • 文件偏移是重新安排的。
  • guard page 被零填充。
  • 运行时修改过的代码页反映的是 dump 时刻状态。

它的主要价值是：

保持内存虚拟偏移 -> 让 IDA 正确建立函数和数据交叉引用

22. 如何识别 MD5 和 SHA-512

22.1 识别 MD5

md5_digest 初始化区包含：

01 23 45 67 89 ab cd ef fe dc ba 98 76 54 32 10

按小端序解释为：

0x67452301
0xefcdab89
0x98badcfe
0x10325476

这是标准 MD5 初始向量。

22.2 识别 SHA-512

sha512_digest 引用了：

08 c9 bc f3 67 e6 09 6a
3b a7 ca 84 85 ae 67 bb
...

按小端序解释后以：

0x6a09e667f3bcc908
0xbb67ae8584caa73b

开头，这是标准 SHA-512 初始向量。

22.3 识别小写 hex

bytes_to_lower_hex 对每个输入字节：

  1. 取高 4 位。
  2. 取低 4 位。
  3. 0-9 加 '0'。
  4. 10-15 转成 'a'-'f'。

另一个常量表也直接包含：

0123456789abcdef

因此可以确认摘要最终使用 Python hexdigest() 相同的小写十六进制形式。

来自 Java 的原始用户 UID：

Java 层没有先拼接或哈希。

当前版本动态得到：

24.1 第一步：分别计算三个 MD5

24.4 第四步：链式选择 8 个字符

初始化：

result = ""

执行 8 轮。第 i 轮：

这里的 & 0x0f 表示只保留 ASCII 编码的低 4 位。

25. Python 独立实现

完整实现位于：

calculate_s.py

核心代码：

import hashlib


def md5_hex(value: str) -> str:
    return hashlib.md5(value.encode("utf-8")).hexdigest()


def calculate_s(uid: str, secret32: str, device_code: str) -> str:
    uid_md5 = md5_hex(uid)
    secret_md5 = md5_hex(secret32)
    device_md5 = md5_hex(device_code)

    primary = hashlib.sha512(
        (secret_md5 + device_md5 + uid_md5).encode("ascii")
    ).hexdigest()

    selector = hashlib.sha512(
        (device_md5 + uid_md5).encode("ascii")
    ).hexdigest()

    cursor = 0
    result = []
    for round_index in range(8):
        cursor = ord(selector[15 * round_index + cursor]) & 0x0F
        result.append(primary[15 * round_index + cursor])

    return "".join(result)

27. 本次最值得复用的分析经验

27.1 从业务数据流开始，不从加密函数开始

最有效的顺序：

请求参数写入点
  -> Java 字段赋值
  -> Java wrapper
  -> native 声明
  -> so 名称
  -> JNI 注册
  -> 真实函数地址
  -> 算法调用链

如果直接搜索 MD5、SHA、AES，通常会遇到很多无关结果。

27.2 静态分析负责提出假设，动态分析负责给出事实

静态分析告诉我们：

  • 存在手工 ELF Loader。
  • 隐藏入口保存在哪里。
  • 隐藏入口在哪里被调用。
  • 可能存在动态注册。

动态分析确认：

  • 隐藏 JNI_OnLoad 的绝对地址。
  • RegisterNatives 的真实表。
  • nativeNewCalculateS 的真实函数指针。
  • 三个 mode 3 输入。
  • MD5 和 SHA-512 的真实中间值。

27.3 地址必须同时记录绝对值和相对值

推荐统一格式：

absolute runtime address
module/image base
relative to mapping base
relative to image base
relative to load bias

只记录绝对地址，下次运行几乎无法复用。

27.4 控制流混淆先看副作用

本次大量随机整数只是状态机常量。真正有价值的是：

  • JNI 函数表调用。
  • GetStringUTFChars / NewStringUTF。
  • MD5 初始向量。
  • SHA-512 初始向量。
  • 字符串拼接。
  • 最终写入输出缓冲区。

27.5 出错时一次只验证一层

spawn 超时时的正确拆分：

ADB 是否正常
Frida transport 是否正常
server 是否稳定
最小 spawn 是否成功
脚本语法是否正确
脚本 API 是否兼容
目标 hook 地址是否正确
dump 时机是否正确

这样可以把“系统环境问题”和“逆向逻辑问题”分开。

27.6 运行时内存对象字段可能被复用

最初根据加载阶段代码，将 loaded-image 的某些字段解释为 size、base、load bias。但在后续 prelink/link 阶段，这些字段会被复用为其他指针。

因此：

某个字段在一个时间点的含义，不代表整个生命周期都不变。

动态读取出异常超大 size 时，应回到所有写入点检查，而不是强行相信早期结构体推断。

27.7 dump 需要关注时序和自修改代码

同一个地址在：

  • JNI 注册前。
  • 第一次调用前。
  • 第一次调用后。

可能具有不同内容。保存多个阶段的快照有助于识别 trampoline、自解密和自修改代码。

6. 为什么 LineageOS boot 无法直接启动当前 PE

首次通过以下命令临时启动 LineageOS 生成的完整 boot：

设备卡在 Sony 第一屏。强制重启后重新进入原 PixelExperience。

6.1 根因

Android boot image 不只有内核，还包含 ramdisk。LineageOS boot 中包含 LineageOS ramdisk，而设备 system 分区仍然是 PixelExperience。

以下组件可能不匹配：

  • init 配置
  • fstab
  • SELinux policy 装载流程
  • vendor service 启动规则
  • system/vendor/ramdisk 之间的接口

所以“LineageOS boot 无法启动 PE system”不能证明新内核有问题。

6.2 恢复方法

fastboot boot 是临时加载，不会覆盖 boot 分区。设备可通过以下方式恢复：

长按 电源键 + 音量上键，直到连续震动三次

重新正常开机后仍会使用原 boot 分区。

6.3 知识点

  • fastboot boot image.img：临时启动，通常不写分区，适合测试。
  • fastboot flash boot image.img：永久写入 boot 分区，测试阶段不应优先使用。
  • 单独替换 boot 并不等于安装完整 ROM。
  • 验证“内核是否可启动”时，应尽量保持 ramdisk 和 system 不变，只替换 kernel。

8.2 v3.3.0 失败

KernelSU-Next setup 脚本默认检出最新 tag，当时为 v3.3.0。

编译错误：

unknown type name 'syscall_fn_t'
fatal error: 'linux/compiler_types.h' file not found

根因

v3.3.0 的 arm64 syscall hook 依赖较新的 syscall wrapper ABI，包括：

  • syscall_fn_t
  • __arm64_sys_* 风格 syscall
  • 新版 syscall table 调用约定
  • 新内核头文件 linux/compiler_types.h

Linux 4.4 的 arm64 syscall table 和函数签名与新内核不同。该问题不是补一个 typedef 就能安全解决，因为实际调用 ABI 也不一致。

解决方法

放弃 v3.3.0，改用带 legacy 后缀的旧内核兼容 tag。

8.4 Linux 4.4 兼容补丁

问题一：ERR_PTR 隐式声明

错误：

include/linux/bpf.h: implicit declaration of function 'ERR_PTR'
static declaration of 'ERR_PTR' follows non-static declaration

根因：KernelSU 的 setuid_hook.c 在包含 linux/err.h 前包含了 linux/bpf.h。该 4.4 内核的 bpf.h 假设 ERR_PTR 已经声明。

解决：在 linux/bpf.h 前加入：

#include <linux/err.h>

文件：

KernelSU-Next/kernel/hook/setuid_hook.c

问题二：不存在的 sched UAPI 头文件

错误：

fatal error: 'uapi/linux/sched/types.h' file not found

根因：uapi/linux/sched/types.h 不存在于当前 Linux 4.4 树。

解决：删除该 include：

#include <uapi/linux/sched/types.h>

文件：

KernelSU-Next/kernel/selinux/rules.c

问题三：in_compat_syscall() 不存在

错误：

implicit declaration of function 'in_compat_syscall'

根因：该 API 来自较新内核，Linux 4.4 arm64 使用 is_compat_task() 判断当前是否为 compat 任务。

解决：

in_compat_syscall()

替换为：

is_compat_task()

文件：

KernelSU-Next/kernel/runtime/ksud_integration.c

为了隔离日志，执行过：

验证状态：

adb shell getprop init.svc.vendor.nfc_hal_service

输出：

设备重启后 NFC HAL 通常会由 init 重新启动。

知识点

  • logcat -b crash 是环形缓冲区，频繁崩溃会覆盖旧记录。
  • 原生进程崩溃的完整信息通常位于 /data/tombstones/。
  • 排障前应先停止无关的崩溃循环，否则容易把错误归因到错误的组件。
  • 仅根据“应用闪退”现象无法判断是 Java、JNI、SELinux、seccomp 还是内核接口问题。

  2. 对比打包前后的 kernel SHA-256。

刷机以及root自用教程

发表于 2026-01-13 更新于 2026-01-19

从去年到现在，我入刷机这个圈子也有小一年了，总说从刷机小白变成刷机大佬只需要一次黑砖，但实际上我也是砖了几十次才慢慢了解到其中的各种原理的，现在算是半只脚入了这个门槛了，这篇博客会跟随我以后的刷机经历不断更新的，以后相关的内容都会添在后续。

0.刷机前的必要准备——解锁bootloader

我之前刚开始刷机的时候使用的设备是红米的note7，那时候小米的解锁政策还很松，大部分时候我还是会推荐用小米系的手机来玩机配环境什么的，但是现在国内几大厂商我只推荐魅族和一加，小米在今年元旦的时候在小米社区已经把申请bl相关的模块完全删除找不到了，也就意味着小米发烧时代完全落幕，传统ov以及底下两个子品牌realme和iqoo也是完全没有解锁的渠道（以上说法排除漏洞解锁的情况），一加虽然加了一层申请政策，但是目前申请难度还是比较低的，基本都能解，魅族手机有内置残血root，酷安某贼大佬的煤油工具箱还能提供解锁相关的功能，所以总体门槛不高，刷机搞root的主体现在就以洋垃圾机型以及漏洞机型还有老小米的为主，这里以小米系举例（因为别的牌子我也没用过），老机型就是先给设备绑定账号，然后使用小米官方解锁工具miunlock进行解锁操作，解锁会清空手机数据，需要提前备份好重要数据，新设备能解都是靠漏洞了，这里就不做讨论

Q:为什么要解锁？

A:BL锁是厂商的一种安全机制，bootloader是在手机通电后最先启动的引导程序，负责初始化各种硬件驱动之类的程序，bl锁相当于是对系统的分区和镜像加了一层验证，使其只能加载运行官方签名的系统和分区镜像（比如一会会说到的recovery，还有boot之类的分区镜像），拒绝所有第三方分区和镜像（这就意味着刷机权限锁死，如果用某些方式强刷会因为签名验证不通过导致黑砖，这种很难办），这样大大降低了恶意软件、病毒通过底层系统侵入的风险，保护用户数据和厂商系统的完整性。

*补：新版本一加似乎也加了防回滚熔断机制，不知道具体还好不好刷

1.解锁后的第一步——明确卡刷和线刷的概念

卡刷是在早期普遍有sd卡的时候得名，相当于把刷机包放在存储设备中再接入手机，执行对应的解包和刷机操作，现在不用内存卡了，把刷机包放在内部存储空间也是同理，这是现在手机官方系统更新常用的方式，这里就能引入一个新的概念，那就是recovery模式（恢复模式），这个模式独立于主系统运行，普通用户能使用到的官方recovery一般只有恢复出厂设置这样的选项，来解决没解锁bl情况下的一些黑砖问题，现在的卡刷基本都是用第三方的recovery来完成的

线刷是使用数据线来进行刷入，一般线刷包会包括多个分区文件，得进入fastboot模式进行每个分区的刷入，一般对刷机比较开放的厂商都会有自己的刷机工具（如miflash）或刷机脚本，如果是进9008深刷的话一般用刷机匣等工具（9008概念一会说）

Q:recovery启动的原理以及结构是什么？

A:一般由四个部分组成：精简Linux内核、ramdisk（虚拟内存盘）、recovery主程序、资源文件

系统中的分区结构如下

分区名称 作用
/boot 存放主系统的内核和引导文件。
/system 存放 Android 操作系统本身（UI、应用等）。
/recovery Recovery 专属领地，与 /boot 并列独立。
/data 存放你的照片、微信聊天记录和 App。
/cache 存放系统运行产生的临时垃圾。
/misc 关键桥梁。存放启动标志位（比如：下次开机是进系统还是进 Recovery）。

关于其是如何启动的，正常来说长按电源加音量（上下键可能不同厂商不一样）时，手机会先启动bootloader引导程序，然后检查/misc分区的指令或者判断你物理按键的组合（可能由主板结构决定），如果识别到recovery请求，就不会加载进boot分区，而是直接加载进recovery分区，然后recovery内核启动，最后让屏幕上显示操作菜单

adb sideload 刷机包名/路径.zip

Q:啥是sideload刷机，什么原理？

A:普通的“卡刷”需要你先把 ZIP 包拷贝到手机存储卡中，然后让 Recovery 去读取和安装。而 Sideload 的原理是建立一条直接的数据通道：

PC 端 (Sender)：电脑通过 adb 协议充当发送者，读取本地的 ZIP 文件并将其分块发送。

手机端 (Receiver)：手机进入 Recovery 的 Sideload 模式，充当接收者。它并不把接收到的文件“存”到 SD 卡上（或者只存入临时缓存区），而是直接读取数据流进行解压和安装。

当手机系统崩溃无法开机，且无法连接电脑传输文件到 SD 卡时（无法挂载 MTP 模式），Sideload 是唯一的“卡刷”救命稻草，因为它不需要进入系统，也不依赖 SD 卡的文件系统是否正常。对于不支持外置 SD 卡且内置存储已满，或者数据分区已加密无法读取的情况，Sideload 可以直接从电脑端读取数据。

6.后续操作以及救砖

刷机到这一步，如果能开机的话就算结束了，刷机是很简单的，但是，很多情况下没这么好开机。

刷不带gapp的类原生很多时候会出现网络连接相关的问题，这时候需要在开机前刷入对应安卓版本的gapp包，把谷歌全家桶安排上之后就可以基本解决网络断联问题。

救砖相关的内容，我这里分几种常见情况来说：

1.卡一屏，或者二屏，能进rec：这种情况优先尝试格式化data，先格了看看能不能开机，如果之前刷入的操作都按着包的作者来做的话，格式化完data基本都能开机，如果开不了的话很有可能是包有些问题，比如rec版本不匹配之类的，这时候如果比较着急的话先刷自己手机系统的官方固件，能线刷尽量线刷，如果没线刷包就卡刷，还得注意一下rec版本是否匹配。

2.卡一屏，进不了rec：这种的话可能会直接跳到fastboot页面，可以先尝试重刷一下rec，看看能不能进，能进的话就给它格式化data再看看开不开得了机。如果这种rec也进不去的话，就通过线刷官方包的方式刷回去能救，比如miflash就能刷，如果线刷包没有脚本的话，就手动把几个重要的img镜像给使用fastboot flash指令刷入，再看看能不能开机。

3.卡一屏，进不了fastboot，或者干脆不亮：这种就算是比较严重的砖了，正常刷是遇不到这种情况的，如果你的手机支持物理按键强制进入9008工程模式的话，那就按照官方办法把手机接入电脑，查看9008端口是否启用，有启用的话一般使用某贼大佬开发的刷机匣，导入对应引导文件，刷回救砖包或官方线刷包就能救。如果这种没办法的话，一般建议用支持的9008工程线试试，天玑系列芯片的话也有进入工程模式的方法，原理相同，这里不过多赘述。如果工程模式都进不了的话，那只能是通过拆机短接的方式来进工程模式刷了，但是这种情况没专门的工具不建议自己动手，建议是拿钱消灾了。

Q:什么是9008模式，刷机原理是什么？

A:9008 模式（官方名称为 Qualcomm HS-USB QD-Loader 9008）是高通（Qualcomm）芯片手机特有的一种底层刷机模式，也被称为 EDL 模式（Emergency Download Mode，紧急下载模式）。权限极高：它直接跳过了系统的层层校验，允许电脑向手机的闪存（存储芯片）里直接写入底层镜像文件。普通刷机（如 Fastboot 或 Recovery）运行在手机的二级引导程序或系统分区上。而 9008 模式运行在高通芯片（SoC）固化在硬件里的 PBL (Primary Boot Loader，初级引导程序)。硬件固化：PBL 是一段烧死在芯片只读存储器（ROM）里的代码，无法被用户删除或损坏。启动机制：当手机启动时，如果发现闪存里的引导文件损坏，或者检测到特定的硬件触发信号（如短接 Test Point 或特殊的刷机线），CPU 就会自动进入 9008 模式。此时手机就像一台只有 CPU 和 USB 接口在工作的“裸机”，不依赖闪存里的任何系统。

第一阶段：Sahara 协议 (握手)

手机连接电脑后，会识别为 Qualcomm HS-USB QD-Loader 9008 端口。此时，电脑端软件（如 QFIL 或 MiFlash）通过 Sahara 协议 将一个被称为 Programmer（引导加载程序，通常是 .mbn 或 .elf 文件） 发送到手机的 RAM（内存） 中运行。

关键点： 这个 Programmer 必须经过手机厂商的数字签名验证，否则无法运行。

第二阶段：Firehose 协议 (数据灌输)

一旦 Programmer 在内存中成功运行，它就会启动 Firehose 协议。这是一个基于 XML 指令的通信方式。

电脑发送 XML 指令告诉手机：“请把这个 4GB 的系统镜像写进 UFS/eMMC 闪存的第 X 扇区”。

Programmer 接收指令，直接绕过 Android 系统，将镜像文件精准地“填”进手机的存储分区。

为什么它能“救砖”？

普通刷机就像是给正在运行的房屋（系统）换门窗，如果地基（引导分区）坏了，你就进不去了。
而 9008 刷机相当于施工队直接空降到地基现场：

  1. 完全跳过闪存限制：即使闪存被格式化、分区表丢失，只要 CPU 没坏，就能重写分区。

  2. 不依赖 Bootloader 锁：在许多老旧机型上，9008 模式可以绕过 Bootloader 解锁权限（虽然近年来厂商加强了服务器验证）。

  3. 直接读写物理扇区：它可以对存储芯片进行最底层的擦除和写入。
